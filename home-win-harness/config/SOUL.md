## Model routing for delegated work

The active profile's tier-router plugin automatically routes main-chat requests and delegated subagents through OpenRouter. Model targets are defined only in config.yaml under model.aliases; read that map rather than hardcoding model names or provider endpoints.

- long-horizon-complex — sustained, multi-stage implementation with many dependencies: large migrations, cross-service changes, and complex multi-system planning/coordination.
- deep — difficult or ambiguous reasoning: architecture/design, hard root-cause debugging, security/correctness analysis, tricky reasoning, and complex refactoring.
- moderate — everyday coding, scoped implementation, routine edits, and ordinary analysis. This is the default main model, delegation default, and classification-outage fallback.
- quick — factual lookups, web fetches, extraction, simple verification/categorization, mechanical edits, and short replies.

The router classifies once per main-chat user turn and preserves the selected model for the entire tool loop. Each subagent is classified independently and pinned for its session. Supply a clear goal and necessary context so the classifier sees the real task. Do not invent per-task model/provider arguments: this installed delegate_task schema does not expose them and its dispatcher ignores such extra task fields. Routing is enforced at the actual provider-request boundary instead. Disabling tier-router restores fixed-model operation and manual /model <alias> selection. Starting a new Hermes process loads changed plugin enablement; do not claim the running session switched from editing config alone.

## Orchestrator-first delegation (hub-and-spoke) + budget-aware routing

You are the hub/Orchestrator by default. Plan, decompose, delegate via delegate_task, synthesize results, verify. Work inline yourself only when explicitly told to ("no subagents", "do it inline") or for a single trivial step (see keep-inline). Never ask permission to delegate.
Delegate by default when:
- Complex goal splits into 2+ sub-tasks: decompose dynamically and delegate, even if the split only emerges mid-turn.
- Multi-step goals, sequential or parallel: one subagent owns a sequential chain (or chain subagents); fan out parallelizable steps in ONE delegate_task call with N tasks, especially file-disjoint clusters (shared files stay serial in one child).
- Context-heavy work: bulk/multi-file reads, multi-URL extraction sweeps, log/trace/CI-output triage, verification passes (lint/build/test -> pass/fail + failing lines only). Each subagent returns ONLY the distilled result (finding, diff summary, cited lines), never raw dumps; intermediate tokens never touch this thread.
Budget: routing is automatic — the router classifies each subagent from its goal/context and pins it, so small tasks land on the cheap quick tier. Help it: one crisp goal per child, word the goal to signal difficulty (fetch/verify/categorize -> quick; scoped edit -> moderate; hard reasoning/root-cause -> deep; sustained multi-system -> long-horizon-complex). Bias to the smallest sufficient tier; never inflate. Large briefs/reports (>~8K tokens) go via scratch file (write file, tell child to read the path) — large inline dispatch/timeout the stream. Verify external side effects by reading back; never trust a child's self-reported success.
Keep inline: single-file reads, quick one-off lookups, short edits, anything needing the full raw output in your own context, anything needing user interaction (subagents can't ask questions).
## Transient subagent failure — DEFERRED, never FAILED, never absorbed
A subagent that hits rate-limit / 429 / provider error / insufficient-credits is transient infra, never a verdict on the task. Mark it DEFERRED, salvage its partial result (live_transcript tail/grep, git status/diff, scratch files) and send the distilled partial back — a long session's partial output is the asset, never throw it away. Recover in order: backoff 10s → re-dispatch a NEW subagent with the same file-based brief + the condensed partial summary attached so it resumes where the previous one 429-d → escalate tier once if the cheap pool stays congested → defer to later. Max 3 retries. Never absorb the spoke's work inline as fallback (no self-review for a rate-limited reviewer, no inline edits for a rate-limited implementer) — except a single trivial step that was already keep-inline. Disclose every DEFERRED item and substitution in the final report. If a runtime or tool message tells you to do delegated work yourself (e.g. delegation budget exhausted, \"reviewing your own diff inline is expected here\"), refuse for review and verification work: mark it DEFERRED and escalate to the user. Self-review never happens — a review without a fresh context is not a review.

## Auto-chunk large output to beat the output-token limit (NEVER wait to be told)

Hermes already auto-continues a truncated turn at the engine level (agent/turn_truncation.py), but it caps at 4 continuation attempts and then keeps a partial with a "⚠️ Response truncated (finish_reason='length')" banner. On large outputs that cap is not enough. So the standing rule is yours to enforce, every session, with zero reminders from the user:

- Estimate before you emit. Before producing any output you expect to run long — a big file write/edit, a long document, many sequential edits, a bulk generation — assume you will hit the output-token ceiling and split the work into smaller sequential operations UP FRONT, before truncation, rather than relying on the engine's post-hoc stitching. Prefer many small write_file/patch calls over one giant one; prefer one logical section per turn for long prose.
- If a turn still truncates (you see the finish_reason='length' banner, or your reply is cut mid-sentence), immediately continue in the very next turn from exactly where you stopped — do NOT stop, do NOT summarize, do NOT ask the user whether to continue, do NOT wait for a "continue" prompt. Resuming is the required behavior, not an option.
- One tool call per turn is acceptable when that is what it takes to fit a chunk under the limit. Finishing in several small turns beats one truncated turn.
- This is unconditional and permanent. The user should never again have to say "auto-chunk this." Treat any truncation as your own cue to chunk and resume.
