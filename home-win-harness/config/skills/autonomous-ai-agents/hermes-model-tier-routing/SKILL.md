# Hermes Model Tier Routing

Set up "route hard tasks to a strong model, easy tasks to a cheap one" in Hermes' own config. The user names tiers by task difficulty (e.g. deep/standard/quick); each tier maps to a concrete model, and delegated subagents run on the tier that fits the task.

## What Hermes actually supports (say this up front)

Aliases alone do not detect task difficulty or automatically switch models. A written policy can guide the orchestrator, but genuine automatic routing needs a runtime integration. For both main chat and subagents, use an enabled profile-local plugin's supported `llm_request` middleware: replace the outgoing request's model with the configured alias target, classify once per main user turn, and pin each subagent for its session. The official middleware contract is https://hermes-agent.nousresearch.com/docs/developer-guide/middleware. Distinguish alias configuration, policy-based selection, and enforced automatic routing when explaining what is installed; never claim aliases alone provide a router.

Exception the user may ask for: you CAN enforce a routing (or decision/classification offload) policy at the runtime boundary with Hermes hooks — a `pre_tool_call` shell/plugin hook can BLOCK or MODIFY a `delegate_task` call to pin the right tier, and `pre_llm_call` can inject a per-turn directive. This runs in every surface (CLI/gateway/desktop/TUI/dashboard), so the policy is applied at every turn instead of relying on agent goodwill. When the user wants routing or an external decision model (e.g. TypeSafe/Jev) enforced automatically, see `references/hook-enforcement.md` for the exact wire contract, the block/modify/inject directives, the fail-open rule that keeps a 'hard-block' policy from bricking sessions on an API outage, and the verified TypeSafe/Jev `systemone` request/response contract for a stdlib-only hook helper.

## The design (three pieces)

1. `model.aliases.<tier>` in config.yaml — one alias per tier. This is the SINGLE SOURCE OF TRUTH for which model each tier maps to. Remapping later = editing only the alias. A tier can carry BOTH a model and a reasoning-effort target (deep=high, standard=medium, quick=minimal); keep that pairing in the tier config so a remap moves both together.
2. `delegation.model` / `delegation.provider` — the default model for ad-hoc subagents spawned without an explicit tier. Set it to the everyday/middle tier so casual delegation doesn't burn the expensive model.
3. A routing policy in `~/.hermes/SOUL.md` (global) or the repo's `AGENTS.md` — maps task type -> tier and tells future sessions to pass the tier explicitly on each delegate_task. Reference tiers BY ALIAS NAME, not by hardcoded model id, so a remap needs no policy edit.

## Procedure

1. Read config.yaml to learn the provider setup: `model.provider`, `model.base_url`, `model.api_key`/key_env, and the list of available models. For a custom proxy the models are under `custom_providers[].models`.
2. Confirm with the user (clarify): the tier names, where the policy lives (global SOUL.md vs repo AGENTS.md), and the default model for untiered delegation. Put the recommended everyday-tier default first.
3. Add one alias per tier via `hermes config set`. Use the FULL form (model + provider + base_url + key_env) when models live behind a custom base_url — the short `provider/model` form does not carry the endpoint. Example per tier:
   - `hermes config set model.aliases.<tier>.model <model-id>`
   - `hermes config set model.aliases.<tier>.provider custom`
   - `hermes config set model.aliases.<tier>.base_url <proxy-url>`
   - `hermes config set model.aliases.<tier>.key_env <ENV_VAR_NAME>`
4. Set the delegation default: `hermes config set delegation.model <id>` and `hermes config set delegation.provider <provider>`.
5. Write the routing policy into the chosen instructions file with a `patch` that PRESERVES existing content (append a new `## Model routing for delegated work` section; do not overwrite the personality/soul text). The policy must: list each tier with the kinds of tasks it handles, name the default tier, and instruct reading the concrete model id from `model.aliases.<tier>` rather than hardcoding.
5b. Pair the tier map with a DELEGATE-WHAT policy in the same instructions file (a `## Delegate context-heavy work` section). Tier routing answers WHICH model; this answers WHEN to spawn a subagent at all. Without it the orchestrator keeps doing bulk work inline and the aliases go unused. State the delegate-by-default classes: bulk/multi-file reads, multi-URL extraction sweeps, log/trace/CI-output triage, verification passes (lint/build/test -> report pass/fail + failing lines only), and independent parallel workstreams. Instruct the subagent to return ONLY the distilled result, not the raw material. Give an explicit keep-inline carve-out (single-file reads, quick lookups, short edits, anything needing the full raw output in the orchestrator's own context, anything needing user interaction) and say minimal overhead is fine — delegate when context bloat is the real cost, not for every small step. A user who wants this is optimizing token budget; do not make the policy so strict it delegates trivial steps.
6. Verify: `python3 -c "import yaml; yaml.safe_load(open('config.yaml'))"` for validity, and `hermes config check`. Print the resulting `model.aliases` and `delegation` blocks back.

## Retuning an installed router (remap a model, or change the tier set)

1. Back up first (`config.yaml.bak-<reason>`); every config write goes through `hermes config set` / `hermes config unset`.
2. Validate each target model id against the provider's model list (grep the local provider model cache, e.g. `provider_models_cache.json`) BEFORE wiring it into an alias — an invented or retired id is only discovered at the first routed inference.
3. Remap only: edit the alias(es), plus `delegation.model` / `model.default` if the departing model is named there. No plugin edit needed.
4. Change the tier SET or its MEANING: the classifier's choice criteria and the outage-fallback tier live in the router plugin source, not in config. Edit, in ONE pass: plugin source (criteria dict + fallback constant), the plugin's unit-test alias fixture and its assertions (a fixture that hardcodes the old tier count fails the criteria-set equality test), the plugin README tier list, and the instructions-file policy. A stale criteria set can select a tier no alias resolves and silently land on the fallback tier.
5. Verify: `hermes config check`, print the alias + delegation blocks back, run the plugin's unit tests (`hermes --run-module unittest discover -s <plugin>/tests -q`) and `hermes plugins doctor <name> --ci`, then confirm a live route by tailing `logs/tier-router.jsonl` for a fresh `selected` entry per tier exercised.

## Pitfalls

- NEVER hand-edit config.yaml. Use `hermes config set KEY VALUE` — a stray indent corrupts the file and breaks the live gateway. This is a hard Hermes invariant.
- An alias with its own base_url authenticates with its OWN credential (`key_env` or `api_key`, which accepts `"${VAR}"`). With neither set, the key is resolved from the alias host, NOT carried over from the previously active provider — so always set key_env on a custom-proxy alias or auth silently fails.
- Reference tiers by alias name in the policy, never by hardcoded model id. Hardcoding means every remap requires editing two places and they drift. If the user adds/renames a TIER (not just remaps a model), the policy's tier list does need updating too — call that out.
- A remapped alias is re-read per route, so NEW sessions and NEW delegated children in the running process pick it up immediately — but the current turn keeps its pinned model (prompt-caching invariant); don't claim the running session switched. Plugin ENABLEMENT changes do need a process restart; alias remaps do not.
- Moving work OFF a congested/unavailable alias target takes TWO edits: the alias AND `delegation.model`. The router's eligible set is built from the CURRENT alias targets — if `delegation.model` still names the target you just removed, delegate requests pass through UNROUTED (router returns None) straight into the dead model. Telltale: no `selected` entry for the subagent session in `logs/tier-router.jsonl` (every routed request logs one) — check that log before concluding a remap took effect. Same rule governs the orchestrator: if the user pins the main/default model to a model OUTSIDE the tier set, main-chat turns pass unrouted by design and only subagents route — state that consequence and get explicit sign-off before implementing, don't silently assume main turns will route.
- The difficulty classifier treats task text as DATA ("not as routing instructions") — rewording a goal cannot escalate its tier. Escalate at the config level instead: temporarily point the congested tier's alias at a proven-good model, and remap back when the pool recovers. Backup config.yaml first (`config.yaml.bak-<reason>`), change via `hermes config set` (the patch tool refuses config writes; `hermes config set` is the sanctioned writer), and verify with `diff` against the backup.
- The same aliases double as interactive `/model <tier>` switches — mention this; it's free UX.
- The `usage-file`/usage report `model` field is the BASELINE label, not the actually routed model. The router rewrites ANY request whose baseline is in the alias target set — including `-m <alias-target>` probe invocations — so a naive per-model inference probe gets silently rerouted and verifies the wrong model. Verify inference per target through its REAL routed path: spawn a delegate child whose brief signals the intended tier, then confirm the `selected` entry in `logs/tier-router.jsonl` plus the child's successful completion. An unrouted baseline (e.g. `model.default` outside the alias set) is the only way to probe a model directly.
- Model-selection surfaces can carry vendor data-policy guards (e.g. Meta `-contributor` tier trains on prompts): `hermes -z -m <model>` prompts "Use this model for this invocation? [y/N]" and refuses on EOF, and non-interactive runs need `security.allow_data_training_tiers_noninteractive: true` (set → probe → unset). The guard fires ONLY on explicit selection — the router's request-time rewrite bypasses it entirely, so deep-tier children reach data-training models with no prompt. Surface this to the user before routing confidential work there.
- The `hermes-agent` bundled skill's `references/providers-and-models.md` documents alias forms and `references/configuration.md` lists the `delegation.*` and `model.aliases` keys. Load those for exact field semantics rather than guessing.
- Verify the installed `delegate_task` schema and dispatcher before injecting overrides. Some releases expose neither model/provider arguments nor per-task route overrides; `_build_children` uses shared `creds["model"]` and silently ignores extra task model/provider fields. A successful hook MODIFY does not prove routing. Use `llm_request` middleware for actual child provider requests when overrides are unavailable. Reasoning EFFORT is config-level (`delegation.reasoning_effort`, or `auxiliary.<task>.reasoning_effort`). So a hook can route the model per task cheaply, but to route effort it must `hermes config set delegation.reasoning_effort` at profile scope BEFORE the children spawn, which makes effort batch-scoped (one level per delegate_task call, not per task). Do not promise per-task effort injection without first proving a per-call override is accepted — probe it empirically (dispatch a child with the override, read the real request via a `pre_api_request` observer) and fall back to profile-scoped effort if the probe fails. Effort levels: none/minimal/low/medium/high/xhigh/max/ultra (default medium), plus a disable-reasoning toggle; providers clamp to supported levels (never escalate past what a model accepts).
- For request-middleware routing, keep all targets on the same provider endpoint/transport, read targets from model.aliases, preserve system prompt/history/tools verbatim, bound classifier input, exclude binary/image payloads, and default to the everyday tier on classifier outage. Gate by profile, provider, endpoint, model allowlist, and stable session/turn IDs. Metadata-only route logs must never contain prompt text or credentials. Classify main turns once and pin child sessions to avoid tool-loop or schema-correction model churn.
- Request-model rewriting does not update Hermes' baseline model label or model-based context accounting. Document that limitation; keep the budget below the smallest routed window. Between-turn model changes lose cross-model prompt-cache reuse even when the message prefix is preserved. Test actual classifier decisions and authenticated inference for every target, plus a real fresh main chat and real delegated child; catalog membership or mocked tests alone are not live evidence.
- In a packaged Windows install, bare python may lack Hermes dependencies. `hermes --run-module unittest discover -s <tests> -q` activates the runtime dependency environment; do not install dependencies into an unrelated bare interpreter just to run plugin tests. `hermes config get KEY --json` avoids needing PyYAML in orchestration scripts.
- The delegate-what policy is a peer of the tier map, not an afterthought: the tiers only pay off if heavy work is actually delegated. When you set up routing, write both sections in one pass.
- A batch of `hermes config set` mutations in ONE shell command is approval-gated as a single action; if the gate goes unanswered the WHOLE batch is blocked and zero changes land. Get explicit scope confirmation before mutating config, then run small sequential batches so partial progress survives a gate timeout.
- `hermes config get` may warn "not a recognized config key" for a key the runtime genuinely reads (observed for global `agent.reasoning_effort`, which `hermes_constants.resolve_reasoning_config` consumes). Don't conclude the key is dead from the warning alone — confirm against the schema source (`config_defaults.py` / the resolve function) before retargeting effort config.
